Q1 | Silver models are views because a view stores nothing and is recomputed at each read: it is cheap to build and always reflects the latest bronze data, and silver is only an intermediate cleaning layer. Gold models are tables because they store the result: Power BI dashboards read them all day without recomputing the joins and aggregations, so reads are fast and cheap, and they are rebuilt at each dbt run. One line per folder in dbt_project.yml (+materialized: view / table) decides it.
Q2 | source() reads a table that dbt does not build, declared in sources.yml (here the bronze tables products, orders, order_items loaded by the ingestion lab with COPY INTO). ref() reads another dbt model (e.g. ref('silver_orders')). ref() lets dbt build the dependency graph (DAG): it knows the build order (silver_orders before silver_order_lines before gold), resolves the right schema/database for the target, and draws the lineage. source() adds bronze as the starting nodes of that lineage and enables freshness checks.
Q3 | The failed test was accepted_values_silver_orders_status__paid__refunded: the inserted order 999 had status 'PENDING', which became 'pending' in silver and is not in the accepted list (paid, refunded). The channel test did not fail because 'Online' was lower-cased and trimmed to 'online' in silver, an accepted value. dbt build runs and tests each model in DAG order; when a test on silver_orders fails, dbt marks every downstream node (silver_order_lines, the 3 gold models and their tests, the singular test) as SKIP so bad data never reaches gold. The gold tables kept yesterday's correct numbers for the dashboard.
